# CRM-система (Skillbox, практика 3.0)

Веб-приложение на Django для учёта услуг, рекламных кампаний, потенциальных
и активных клиентов и контрактов. Вёрстка — из выданного архива
`templates_only.zip` (Bootstrap 5), доработанная под требования ТЗ.

## Быстрый старт

```bash
python3 -m venv venv
source venv/bin/activate            # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

### База данных

Проект рассчитан на **PostgreSQL** (требование ТЗ):

```sql
CREATE DATABASE crm;
CREATE USER crm_user WITH PASSWORD 'crm_password';
GRANT ALL PRIVILEGES ON DATABASE crm TO crm_user;
ALTER DATABASE crm OWNER TO crm_user;
```

Параметры переопределяются переменными окружения: `DJANGO_DB_NAME`,
`DJANGO_DB_USER`, `DJANGO_DB_PASSWORD`, `DJANGO_DB_HOST`, `DJANGO_DB_PORT`.

Для быстрой проверки без PostgreSQL: `export DJANGO_USE_SQLITE=1`
(PowerShell: `$env:DJANGO_USE_SQLITE=1`).

### Миграции и тестовые данные

```bash
python manage.py migrate
python manage.py loaddata roles demo_users demo_data
python manage.py runserver
```

Порядок важен: `roles` → `demo_users` (ссылается на группы) → `demo_data`.
Приложение: <http://127.0.0.1:8000/>, админка: <http://127.0.0.1:8000/admin/>.

Если изменили модели: `python manage.py makemigrations && python manage.py migrate`.

### Демо-учётные записи (пароль у всех `Demo12345!`, только для демонстрации)

| Логин      | Роль                         |
|------------|------------------------------|
| `admin`    | Администратор (суперпользователь, доступ в `/admin/`) |
| `operator` | Оператор                     |
| `marketer` | Маркетолог                   |

Свои пользователи и роли создаются штатно через `/admin/` (раздел

заранее создаёт три группы с нужными правами.

## Роли и права

| Роль | Права |
|------|-------|
| Администратор | Суперпользователь: всё + управление пользователями и ролями в `/admin/` |
| Оператор | Лиды: создавать / смотреть / редактировать. Кампании: смотреть (для статистики) |
| Маркетолог | Услуги и рекламные кампании: создавать / смотреть / редактировать |
| Менеджер | Контракты и активные клиенты: создавать / смотреть / редактировать; лиды: смотреть и переводить в активные; кампании: смотреть (статистика) |

По ТЗ роли **не могут удалять** записи (в ТЗ только создание, просмотр,
редактирование). Кнопки «Создать / Редактировать / Удалить» в шаблонах
показываются только при наличии соответствующего права; прямой заход по URL
без права даёт страницу 403. Право на удаление можно выдать любой группе в
админке.

«Все роли смотрят статистику»: у каждой роли есть `advertisements.view_advertisement`,
а страница статистики доступна по этому праву.

## Аутентификация и авторизация

**Аутентификация** — стандартная `django.contrib.auth`: модель `User`,
сессии (`SessionMiddleware`), вход `/accounts/login/` (`LoginView` с шаблоном
`registration/login.html`), выход `/accounts/logout/`. Анонимный пользователь
на любой странице перенаправляется на вход (`LOGIN_URL`), после входа — на `/`.

**Авторизация** — группы и права Django (RBAC):
- Для каждой модели Django создаёт права `add_/view_/change_/delete_<model>`.
- Группы «Оператор», «Маркетолог», «Менеджер» получают набор прав (`fixtures/roles.json`),
  пользователь получает роль через поле «Группы» в админке.
- Каждое представление наследует `PermissionRequiredMixin` с конкретным
  `permission_required` (например `leads.add_lead`). Нет права — 403.
- В шаблонах меню и кнопки скрываются через `{% if perms.<app>.<право> %}`.
- Суперпользователь обходит проверки прав.

## Обработка нестандартных ситуаций

| Ситуация | Поведение |
|----------|-----------|
| Не вошёл в систему | Редирект на `/accounts/login/?next=…` |
| Нет прав у роли | Страница 403 («Доступ запрещён») |
| Несуществующая запись | Страница 404 |
| Удаление записи, на которую есть ссылки (услуга с кампаниями, лид с активным клиентом…) | `ProtectedError` перехватывается, сообщение «Нельзя удалить…», запись остаётся |
| Неверный телефон / email | Ошибка валидации под полем формы |
| Сумма, бюджет, стоимость ≤ 0 | Ошибка валидации |
| Дата окончания контракта раньше даты заключения | Ошибка валидации |
| Повторный перевод лида в активные | Лид и контракт, уже привязанные к клиенту, исчезают из списков выбора; уникальность защищена `OneToOneField` |
| Неверный пароль при входе | Форма входа с сообщением об ошибке |

## Сценарий демонстрации (для записи экрана)

1. Консоль: `migrate`, `loaddata …`, `runserver`; открыть `/`.
2. Без входа открыть `/leads/` → редирект на вход. Ввести неверный пароль.
3. Войти `operator`: видны «Рекламные компании» и «Лиды»; создать лида,
   ввести неверный телефон (ошибка); открыть `/products/` → 403.
4. Войти `marketer`: создать услугу, кампанию; попробовать удалить услугу с
   кампанией — недоступно (нет права); открыть `/leads/` → 403.
5. Войти `manager`: создать контракт с файлом (и с датой окончания раньше
   начала — ошибка); в «Лиды» нажать «В активные» — поле лида предзаполнено;
   сохранить; открыть `/ads/statistic`.
6. Войти `admin`: попытаться удалить услугу с кампаниями — сообщение о
   защите; в `/admin/` показать пользователей и группы.
7. В консоли: `pytest` и `pylint --rcfile .pylintrc crm products advertisements leads contracts customers users`.

## Примечания

- «Период действия» контракта хранится как дата заключения (`start_date`) и
  дата окончания (`end_date`), как в выданном шаблоне.
- Фамилия и имя лида — два поля (по шаблону); отчества нет.
- Связи защищены `on_delete=PROTECT`: история клиентов не теряется при
  случайном удалении справочной записи.
- Django ограничен `<5.0`: шаблон выхода — обычная ссылка (GET).
